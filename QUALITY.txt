ПРАВИЛО ПРИЁМКИ «ПРАКТИКИ» — версия 1

ПРИНИМАЕМ ТЕХНИЧЕСКУЮ ВЕРСИЮ, ЕСЛИ
Один запуск npm run accept завершил два полных зелёных прогона подряд на одинаковых исходниках, тестах, настройках и зависимостях. Оба прогона проверяют типы, данные, сервер, производственную сборку и браузерные сценарии. SHA-256 собранного HTML должен совпасть. Проверяется список выполненных тестов, а не только их количество.

Нет пропущенных, отменённых и помеченных TODO тестов; нет ожидаемых падений, автоматических повторов или ошибок в консоли страницы. Любое падение прерывает приёмку. После исправления начинаем оба прогона заново. Изменение исходников, тестовых материалов, настроек или зависимостей также требует новой приёмки.

Два одинаковых зелёных прогона помогают заметить нестабильность, но не доказывают отсутствие всех ошибок. Слабый тест может быть зелёным сколько угодно раз. Поэтому набор проверяет действия пользователя и содержимое результата: выбранные определения, исключения, связи, источники, промпты, скачиваемый JSON, восстановление и ошибки.

КАК ЗАПУСКАТЬ
Нужен Node.js 24 или новее. Все команды ниже выполняются из папки ui/.
Первый запуск:
  npm ci
  npm run browser:install
Обычная работа после небольшого изменения:
  npm run smoke
Полная диагностика одним прогоном:
  npm run qa
Перед передачей версии:
  npm run accept
Быстрые проверки только данных/сервера/правила приёмки:
  npm test

smoke включает сборку и короткий сквозной путь в браузере на широком и узком экране. Он не засчитывается как приёмка. qa выполняет один полный прогон и тоже не заменяет два приёмочных.

ЧТО ПРОИСХОДИТ АВТОМАТИЧЕСКИ
Тесты создают отдельные локальные серверы и новый браузерный контекст. Рабочие вкладки и профиль пользователя не используются. Браузер запускается без видимого окна. Модель в браузерных сценариях отключена; ошибки модельного протокола воспроизводятся локальным тестовым сервером. Настоящие API-ключи не нужны, учебные тексты наружу не отправляются.

В ui/reports/ у каждого запуска своя папка. report.html — читаемый итог, report.json — машинный протокол. В run-1/ и run-2/ сохраняются журналы, browser.json, снимки и трассировки падений. latest.json указывает на последний запуск; старые результаты не стираются. Если проверка типов/сервера сломалась, браузерные сценарии могут не запускаться — приёмка всё равно красная.

Набор содержит тесты самого правила приёмки: повтор после ошибки, несовпадающие исходники или сборка, другой набор тестов, пропуски и повторные попытки должны оставаться красными.

Для GitHub подготовлен .github/workflows/quality.yml: при push и pull request запускается та же команда npm run accept, отчёты сохраняются даже при ошибке. Для этого папка проекта (с ui/, local/ и .github/) должна стать корнем репозитория. Удалённый workflow в этой сессии не запускался; репозиторий не публиковался. Настройка защищённой ветки и обязательного status-check выполняется отдельно, когда будет выбран репозиторий.

УЧЕБНАЯ ПРИЁМКА — ОТДЕЛЬНО
Текущие зелёные тесты не подтверждают качество настоящей модели. До пилота с заказчиком:
1. Методист выбирает не менее 10 настоящих фрагментов лекций: определения, отсутствие определения, синонимы, спорные формулировки, длинный текст, несколько тем и обязательные термины. Фиксирует ожидаемые темы, определения, источники и допустимые связи.
2. На согласованной модели выполняются минимум 3 независимых прогона каждого фрагмента с записанными версией модели и настройками. В каждом прогоне проверяется отсутствие выдуманных определений и неподтверждённых смысловых связей; все обязательные термины присутствуют или явно требуют уточнения.
3. Числа полноты и точности оцениваются по этой разметке; целевой порог согласуется до прогона. Блокирующие дефекты — искажение обязательного термина, выдуманный источник, неверная предметная связь, потеря правок методиста.
4. Пакет импортируется в действующий тьютор. Проверяются правильный, частичный, неверный ответы слушателя и нехватка данных. Тьютор должен давать обратную связь по материалу и возвращаться к вопросу после подсказки.
5. Два методиста, не участвовавшие в разработке, проходят путь без подсказок. Записываем места остановки, время и объём правок. Ошибки/непонятные действия превращаются в задачи и в автотесты там, где это проверяемо.

КАК ИСКАТЬ УЛУЧШЕНИЯ
Падение сначала воспроизводится и классифицируется: ошибка продукта, теста или окружения. Причину исправляем, а проверку не ослабляем ради зелёного цвета. Если изменился ожидаемый сценарий, обновляем критерий и запускаем новую приёмку. Новые сообщения об ошибках получают воспроизводимый пример. Отчёт показывает наиболее долгие сценарии и оставшиеся области ручной проверки.

Автоматический визуальный эталон, полные WCAG-проверки, Firefox/WebKit, высокая нагрузка и реальные модели пока не входят в обязательный набор. Их добавление требует отдельного согласованного критерия; отсутствие этих проверок указано в отчёте.
